# BG-013 タスク文の Markdown プレビュー(保留)

## 要望

タスク文に Markdown 記法を貼り付けたとき、プレビュー(整形表示)できるようにしたい。

## 状態

**保留**(2026-10-08)。複数行入力(BG-012)の実装後に判断する。

## 懸念事項

1. **外部依存が増える**
   本アプリは素のJSで、ビルド工程も依存ライブラリも持たない。`marked` 等を同梱すると、配布物に第三者のコードが入り、更新追従が必要になる。
2. **HTML注入(XSS)のリスク**
   貼り付けた Markdown や、変換結果のHTMLをそのまま `innerHTML` に入れると、文中のHTMLがアプリ内で実行される。
   `contextIsolation` によりOS機能へは直接届かないが、`window.api`(保存・終了・設定変更)は呼べてしまう。
   ライブラリで変換する場合は DOMPurify 等のサニタイズが必須になる。
3. **外部リンクの扱い**
   リンクのクリックは `shell.openExternal` が必要。許可するスキームを `https` / `http` に限定し、`javascript:` や `file:` を拒否する検証が要る。
   現在の `main.js` は遷移とウィンドウ生成を全て拒否している(`will-navigate` / `setWindowOpenHandler`)ので、この方針との整合を取ること。
4. **画像・外部リソースの読み込み**
   `![](http://...)` を描画すると、開いただけで外部へ通信が飛ぶ(IPアドレスや閲覧の漏えい、追跡)。画像は描画しない方針が必要。
5. **UIとの相性**
   このガジェットは幅300px前後の常駐ウィンドウ。見出し・表・コードブロックは窓に収まりにくく、1タスクの行が高くなる。
   「プレビュー」を常時整形表示にするか、別のトグル/ホバー表示にするかで設計が変わる。
6. **データの保存形式**
   タスク文は素のテキストで保存している。Markdown は「表示時だけ変換する」方針とし、保存形式は変えない(既存データとの互換、検索や編集のしやすさのため)。
7. **編集との整合**
   ダブルクリック編集は `contentEditable='plaintext-only'` で素のテキストを編集する。整形表示とのON/OFF切替や、編集開始時に原文へ戻す挙動が要る。
8. **テスト**
   変換器を自作する場合は、記法ごとの単体テストと「HTMLが実行されない」ことのテストが必須。ライブラリ採用の場合は、サニタイズ設定のテストを置く。

## 方針案(実装する場合)

- **最小構成(推奨)**: 自前の小さな変換器。`**太字**` / `` `コード` `` / `- 箇条書き` / `- [ ]` / `[text](https://…)` のみ対象。
  DOMを `createElement` + `textContent` で組み立て、`innerHTML` は使わない。画像は描画しない。リンクは `https`/`http` のみ。
- **フル構成**: `marked` + DOMPurify を同梱。見出し・表・引用も使えるが、上記 1〜4 のコストとリスクを負う。
